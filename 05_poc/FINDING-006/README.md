# FINDING-006 proof-of-concept files

Generated by [`tools/gen_finding006.py`](../../tools/gen_finding006.py):

```
python3 gen_finding006.py 05_poc/FINDING-006
```

Each variant ships three ways: `.j2k` (raw codestream, for a decoder harness),
`.jp2` (JP2-boxed) and `.pdf` (a one-page PDF whose only content is an image
XObject with `/Filter /JPXDecode` — the zero-click path).

## What the files do

All variants use the same two code-block sizes, both legal per
ISO/IEC 15444-1 and both accepted by the mspdf marker parser:

| | main-header `COD` | tile-part-1 `COC` |
|---|---|---|
| `xcb_raw`, `ycb_raw` | `8, 0` | `0, 2` |
| xcb, ycb | 10, 2 | 2, 4 |
| xcb + ycb (spec limit 12) | 12 | 6 |
| nominal code-block | 1024 x 4 | 4 x 16 |
| `L` | 0 | **0 — unchanged** |

Keeping `L` identical is what matters: `L` is the only field the two tile
decode drivers compare across tile-parts.

| file | image | code-blocks | what it demonstrates |
|---|---|---|---|
| `poc_min` | 4 x 4 | 1 | **the submission PoC.** The holder-A copy length comes from the *nominal* width recorded in the holder, so it is `(1024+2)*4 = 4104` bytes whatever the image size: 4104 bytes written into a 1027-byte allocation, sourced by reading 4104 bytes out of another 1027-byte allocation. |
| `poc` | 1024 x 4 | 1 | the band is 1024 wide, so the *actual* code-block width is 1024 as well and holder B's `memset` overflows by the same 3077 bytes — both tile-component buffers in one file. |
| `poc_tp1empty` | 1024 x 4 | 1 | hedge: tile-part 1 carries a zero-length packet, which parses identically under any code-block grid, so the overflow rests only on the mutated coding style being live at decode time. |
| `poc_spray` | 1024 x 1024 | 256 | 256 code-blocks, so `3*256 + 2 = 770` identically sized 1027-byte pool chunks exist and each code-block iteration writes 4104 bytes. |
| `control*` | — | — | byte-identical to the matching PoC except that the tile-part-1 `COC` is absent (11 bytes shorter, plus the `Psot` adjustment). Isolates the cause. |

## Reference-decoder validation

Two independent, mature JPEG 2000 implementations were run over every file:
FFmpeg 6.x's native `jpeg2000` decoder on the raw codestream, and
OpenJPEG via poppler `pdftoppm` on the PDF wrapper.

| file | FFmpeg (native) | poppler / OpenJPEG |
|---|---|---|
| `control_min` | decoded, 27-byte PGM | rendered |
| `control` | decoded, 4110-byte PGM | rendered |
| `control_spray` | decoded, 1048593-byte PGM | rendered |
| **`poc_min`** | **decoded, 27-byte PGM** | **rendered** |
| `poc` | rejected: `nonzerobits -91 invalid or unsupported` | rejected: `segment too long (4) with max (3) for codeblock 187` |
| `poc_tp1empty` | rejected: `nonzerobits -91` | rendered |
| `poc_spray` | rejected: `Invalid data found` | rejected: `segment too long (4) with max (0) for codeblock 0` |

Two things follow.

**`poc_min` is a conforming file that both reference decoders accept
without a single warning.** With a 4 x 4 image the mutated code-block size
still yields a 1 x 1 code-block grid, so re-deriving the grid from the `COC`
changes nothing about how the packet header parses. There is no "the input
was malformed" counterargument available for it: the only unusual thing in
the file is a legal tile-part `COC` that changes the code-block size, which
is what the specification allows that marker to do.

**The rejections on the other variants show what correct handling looks
like.** OpenJPEG's message names the mechanism exactly: it re-derived the
code-block grid from the tile-part `COC` (4 x 16 code-blocks over a 1024-wide
band gives 256 of them instead of 1) and then walked into inconsistent packet
data. FFmpeg does the same and fails its `nonzerobits` sanity check. Both
re-derive. mspdf does neither: `FUN_18088E7FC`, the later-tile-part re-entry
path, deliberately re-uses the tile-part-0 grid and only shifts its offsets,
while `FUN_1808877AE` re-reads `xcb`/`ycb` from the mutated coding style.

## Expected result on mspdf

Decoding any `poc*` file in a renderer built on `mspdf.dll` 154.0.4258.33
should write 3077 bytes past the end of a 1027-byte pool allocation, inside
`t5::jp2k`'s per-tile-component EBCOT state. The matching `control*` file
should decode normally. This has **not** been observed live; see the
verification notes in the finding.
